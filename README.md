# club_monitor

Параллельно опрашивает серверы одного или нескольких компьютерных клубов
(`GET /api/v1/clients` на каждом хосте) и складывает в единую SQLite-базу
минимум, нужный для аналитики загруженности: **клуб, id места, занято ли
оно, время опроса**.

## Несколько клубов: одна база с `club_id`

Данные всех клубов пишутся в одну базу, каждая запись помечена `club_id`.
Альтернатива — отдельная база на каждый клуб — здесь не выбрана: цель
проекта это аналитика, а значит нужно будет и смотреть на каждый клуб
отдельно, и сравнивать клубы между собой (загрузка по часам, средняя
длительность сеанса и т.д.). С отдельными базами каждое такое сравнение
превращалось бы в `ATTACH DATABASE` или склейку данных на уровне
приложения. Единая база с `club_id` — это на порядок проще для запросов,
а цена вопроса — всего одна лишняя колонка почти везде.

Если в вашем случае клубы должны быть полностью изолированы друг от
друга (разные владельцы, разные требования к доступу) — это единственная
ситуация, где раздельные базы оправданы; тогда достаточно запускать
отдельный контейнер `club_monitor` на клуб со своим `CLUB_DB_PATH`.

## Как задать список клубов

Список клубов — в файле `clubs.json` (шаблон: `clubs.json.example`):

```json
[
  {
    "id": "club1",
    "name": "Клуб на Ленина",
    "host_url": "https://host1.example.com",
    "api_key": "API_KEY_CLUB_1"
  },
  {
    "id": "club2",
    "name": "Клуб на Мира",
    "host_url": "https://host2.example.com",
    "api_key": "API_KEY_CLUB_2"
  }
]
```

`id` должен быть уникальным и стабильным — именно он попадает в БД как
`club_id`, менять его "задним числом" не стоит (старые записи останутся
со старым id). `name` — просто для читаемости в аналитике.

Если `clubs.json` не найден, программа для обратной совместимости
попробует собрать один клуб из переменных окружения
`CLUB_HOST_URL`/`CLUB_API_KEY`/`CLUB_ID` (см. `.env.example`).

При каждом опросе все клубы из списка опрашиваются **параллельно**
(отдельными потоками — запросы к API это ожидание ответа по сети, а не
нагрузка на CPU), чтобы один медленный или недоступный клуб не задерживал
опрос остальных. Запись результатов в SQLite при этом идёт последовательно
в одном потоке — у SQLite один писатель, параллельные `INSERT` из разных
потоков только создавали бы конкуренцию за блокировку.

## Схема БД

**`clubs`** — справочник (id → название), только для читаемости в
аналитике.

**`current_status`** — последний известный статус каждого места в
каждом клубе (одна строка на пару club_id+id). Используется программой,
чтобы на каждом опросе сравнить новый статус с предыдущим.

```sql
CREATE TABLE current_status (
    club_id    TEXT NOT NULL,
    id         INTEGER NOT NULL,
    busy       INTEGER NOT NULL,
    updated_at TEXT NOT NULL,        -- московское время
    PRIMARY KEY (club_id, id)
);
```

**`status_changes`** — журнал переходов "занято ↔ свободно" по клубам:
новая строка добавляется только тогда, когда статус места реально
изменился. По этой таблице удобно считать длительность сеансов (см.
`analytics_queries.sql`, запросы 6-8).

```sql
CREATE TABLE status_changes (
    id         INTEGER PRIMARY KEY AUTOINCREMENT,
    club_id    TEXT NOT NULL,
    seat_id    INTEGER NOT NULL,
    busy       INTEGER NOT NULL,  -- новое состояние после изменения
    changed_at TEXT NOT NULL      -- московское время
);
```

Как это работает: при каждом опросе `main.py` держит в памяти словарь
`{(club_id, id места): текущий busy}` (загружается из `current_status`
при старте). Если пришедший статус отличается от того, что в словаре, -
место считается впервые увиденным или сменившим состояние, и тогда:
1. `current_status` обновляется новым значением;
2. в `status_changes` добавляется строка с моментом перехода.

Если статус не изменился - `status_changes` не растёт, никаких новых
записей за этот опрос не появляется.

## Обновление с версии "один клуб"

Если у вас уже есть `club_stats.db`, заполненная предыдущей версией
(без `club_id`), выполните один раз, ДО запуска новой версии `main.py`:

```bash
sqlite3 club_stats.db < migrate_v1_to_multi_club.sql
```

Все существующие записи получат `club_id='default'`. Чтобы программа
продолжила писать в них же, первый клуб в `clubs.json` должен иметь
`"id": "default"` (или отредактируйте скрипт миграции под нужный id
перед запуском).

## Часовой пояс

Все временные метки (`updated_at`, `changed_at`) пишутся в
московском времени (`Europe/Moscow`, сейчас фиксированный UTC+3).
Хранятся они **без смещения** (`2026-09-10T14:22:25`, а не `...+03:00`)
намеренно: если оставить смещение, SQLite при вызовах `strftime()`/
`date()` в аналитике сам переведёт время обратно в UTC, и все запросы по
часам/дням окажутся сдвинуты на 3 часа.

Если в своём SQL нужно сравнить со временем на сервере СУБД (например,
`strftime('%s', 'now')`) - помните, что `'now'` в SQLite всегда в UTC,
поэтому такие сравнения нужно явно сдвигать на 3 часа
(`strftime('%s', 'now', '+3 hours')`) - пример есть в запросе №3 в
`analytics_queries.sql`.

## Запуск через Docker

Проект готов к запуску контейнером — есть `Dockerfile` и
`docker-compose.yml`. Контейнер сам работает в демон-режиме
(`--interval`) и перезапускается при сбоях/перезагрузке сервера.

1. Подготовьте конфиги:

   ```bash
   cp .env.example .env
   cp clubs.json.example clubs.json
   ```

   Заполните `clubs.json` реальными хостами и ключами (см. раздел
   "Как задать список клубов" выше), в `.env` при необходимости
   поменяйте `CLUB_INTERVAL`.

2. Соберите и запустите:

   ```bash
   docker compose up -d --build
   ```

3. База данных SQLite сохраняется на хосте в `./data/club_stats.db` —
   это volume, он переживает пересборку и перезапуск контейнера.
   `clubs.json` тоже смонтирован как volume (не встроен в образ), чтобы
   ключи API не оказались внутри собранного образа и список клубов можно
   было менять без пересборки — правкой файла и `docker compose restart`.

4. Полезные команды:

   ```bash
   docker compose logs -f          # логи опросов в реальном времени
   docker compose restart          # перезапуск (например, после правки clubs.json)
   docker compose down             # остановить и удалить контейнер (данные в ./data останутся)
   ```

5. Аналитику можно снимать прямо с файла на хосте, без входа в контейнер:

   ```bash
   sqlite3 data/club_stats.db < analytics_queries.sql
   ```

## Установка без Docker (venv + cron)

Если Docker не нужен и вы хотите запускать скрипт напрямую на хосте:

```bash
cd club_monitor
python -m venv venv
source venv/bin/activate      # Windows: venv\Scripts\activate
pip install -r requirements.txt
cp clubs.json.example clubs.json   # и заполнить реальными данными
```

## Запуск

Один опрос всех клубов (для cron):

```bash
python main.py
```

Демон-режим с интервалом:

```bash
python main.py --interval 60
```

### cron (раз в минуту)

```
* * * * * cd /path/to/club_monitor && /path/to/venv/bin/python main.py >> monitor.log 2>&1
```

## Аналитика

Готовые запросы — в `analytics_queries.sql`, всё разбито по клубам:
длительность отдельных сеансов, средняя/мин/макс длительность по месту
и по клубу, а также сколько уже длится сеанс на занятых прямо сейчас
местах.

```bash
sqlite3 club_stats.db < analytics_queries.sql
```
